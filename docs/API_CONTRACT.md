# Контракт интерфейса и бэкенда

> Обновление 19.09.2026: этот документ описывает исходный прототип. Актуальные рабочие места, ручные ограничения, статусы и оборудование описаны в [WORKFLOW.md](WORKFLOW.md), уточнения требований — в [CLARIFICATIONS.md](CLARIFICATIONS.md). Контракт ниже требует расширения этими сущностями при серверной интеграции.

Это предлагаемый контракт для реализации серверной части. HTTP-сервера в прототипе нет: объект `api` в `frontend/src/api.ts` реализует его локально. Единственный источник TypeScript-типов — `frontend/src/types.ts`.

## Планирование

`POST /api/plans`

Тело: `Dataset`.

Ответ: `PlanPair = { baseline: Plan, optimized: Plan }`.

```json
{
  "name": "Москва · Юго-восток",
  "date": "2026-08-17",
  "jobs": [
    {
      "id": "74198",
      "title": "Подключить интернет",
      "address": "Волгоградский проспект, 80",
      "point": [55.704, 37.779],
      "duration": 45,
      "window": ["09:00", "11:00"],
      "priority": "normal",
      "skill": "connection"
    }
  ],
  "engineers": [
    {
      "id": "e1",
      "name": "Алексей Морозов",
      "role": "Универсальный инженер",
      "color": "#6665df",
      "start": [55.739, 37.684],
      "shift": ["09:00", "18:00"],
      "skills": ["local", "connection", "emergency"],
      "transport": "car"
    }
  ]
}
```

Справочники:

| Поле      | Значения                           |
| --------- | ---------------------------------- |
| Навык     | `local`, `connection`, `emergency` |
| Транспорт | `car`, `walk`, `bike`, `transit`   |
| Приоритет | `normal`, `urgent`                 |

Одна заявка требует один навык. У инженера 1–3 навыка, один транспорт. `job.transport` необязателен: отсутствие означает отсутствие ограничения. `point` и `start` — `[широта, долгота]` WGS84. Цвет и роль инженера — поля отображения; импорт назначает значения по умолчанию, если их нет.

## План

```ts
interface Plan {
  id: string;
  routes: {
    engineerId: string;
    stops: {
      jobId: string;
      arrival: number;
      start: number;
      end: number;
      travel: number;
      km: number;
    }[];
    km: number;
  }[];
  unassigned: { jobId: string; reason: string }[];
  metrics: { assigned: number; engineers: number; km: number; travel: number };
}
```

- `arrival/start/end` — целые минуты от полуночи локального дня. `travel` — минуты от предыдущей точки; `km` в остановке — длина соответствующего участка.
- `arrival <= start`, `end = start + duration`. Ожидание разрешено. Начало работы включительно внутри окна; завершение — в пределах смены.
- Маршрут начинается в стартовой точке инженера. Обратный путь после последней заявки в метрики не входит.
- Каждая заявка присутствует ровно один раз: в одном маршруте или в `unassigned`.
- `assigned` — число назначенных заявок, `engineers` — количество непустых маршрутов. Время и пробег — суммы участков. Не округляйте метрики на сервере до суммирования; округление делает интерфейс.
- Причины неназначения должны отличать доказанную нехватку навыка/транспорта от «алгоритм не нашёл допустимый вариант». Не утверждать невозможность по результату одной эвристики.

## Перепланирование

`POST /api/plans/replan`

```ts
{
  dataset: Dataset;
  previous: Plan;
  event: {
    type: "urgent";
    at: string;
    job: Job;
  }
}
```

Ответ:

```ts
{
  dataset: Dataset; // включает новую заявку
  plans: PlanPair;
  previous: Plan;
  changedIds: string[];
}
```

`changedIds` включает заявки, у которых изменились исполнитель, позиция в маршруте или начало работы, а также новые назначения/снятия. UI показывает «было/стало». Для ранее неназначенных заявок также нужен корректный diff статуса.

В демо замораживаются остановки, начавшиеся строго раньше события. Для серверного MVP уточнить и зафиксировать правило для `start == event.at`, завершённых работ и инженера, уже находящегося в пути. Передавать фактическое состояние отдельным полем; не выдавать плановое начало за факт исполнения. Базовый план после события рассчитывать на том же наборе и с теми же замороженными работами.

## Замена адаптера

```ts
async function post<T>(path: string, body: unknown): Promise<T> {
  const response = await fetch(path, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(body),
  });
  if (!response.ok)
    throw new Error(
      "Не удалось рассчитать план. Проверьте данные и повторите попытку.",
    );
  return response.json();
}

export const api: DispatchApi = {
  plan: (data) => post<PlanPair>("/api/plans", data),
  replan: (dataset, previous, event) =>
    post<ReplanResult>("/api/plans/replan", { dataset, previous, event }),
};
```

Перед интеграцией добавить проверку ответа сервера во время исполнения (например, схемой), таймаут, отмену запроса и обработку 422/409/5xx. Для локальной разработки настроить Vite proxy `/api` на FastAPI. Не хранить секреты в переменных `VITE_*`: они попадают в браузерную сборку.

## Следующее расширение контракта

1. `reasonCodes`, человекочитаемые объяснения назначений и явные результаты проверки ограничений от сервера. Сейчас объяснение строится интерфейсом из `Job`, `Engineer` и `Stop`.
2. Геометрия маршрута/участков GeoJSON от движка дорожной маршрутизации; карта сейчас рисует прямые отрезки.
3. Время и расстояние матрицей по типам транспорта, версия источника и признаки упрощённой оценки.
4. Устойчивый `planId`, версия плана и защита от применения устаревшего события.
5. Фактические статусы инженеров и работ, если команда решит моделировать движение в реальном времени.

Эти расширения согласовать до финального подключения; изменение схемы одновременно отражать в `types.ts`, адаптере и проверках.
