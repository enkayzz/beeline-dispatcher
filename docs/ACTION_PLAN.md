# План выполнения кейса «Билайн Бизнес»

## Что нужно получить к защите

Запускаемый веб-прототип, который распределяет заявки с учётом трёх обязательных ограничений, показывает карту и расписание, объясняет результат, перестраивает день после одного события и сравнивается с заданным базовым алгоритмом. Плюс исходный код, README и презентация. Ориентир демонстрации — 5–7 минут.

Промышленная архитектура, авторизация, мобильное приложение и доказательство математического оптимума не нужны. Основной риск — несложный интерфейс, за которым ограничения проверяются лишь визуально. Их должен проверять алгоритм и независимый валидатор.

## Уже подготовлено

- React + TypeScript, четыре экрана, карта, расписание и карточки объяснений.
- Импорт единого JSON, поиск и фильтры, экспорт плана.
- Демонабор и локальный адаптер расчёта, сценарий срочной заявки, diff назначений.
- Общие типы для API и автоматические проверки основного сценария.

Это готовая основа интерфейса. Дорожные маршруты, привязка реальных CSV и серверный оптимизатор остаются отдельной работой.

## Этапы и критерии готовности

Оценки времени ориентировочные, без предположения о фактической длительности хакатона. Внутри команды данные, UI и алгоритм можно вести одновременно после согласования контракта.

| Этап                          | Действия                                                                                                                                       | Результат / критерий готовности                                                                          | Ориентир  |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | --------- |
| 1. Зафиксировать MVP          | Выбрать срочную заявку как единственное обязательное событие. Согласовать семантику окна, смены, приоритета, начатых работ и целей оптимизации | Один список правил, одинаковый для UI и алгоритма                                                        | 30–45 мин |
| 2. Подготовить данные         | Разобрать CSV; определить поля, которых не хватает; получить справочник инженеров или создать описанный синтетический                          | Валидный JSON на один день: 10–15 инженеров, не более 100 заявок; все навыки и типы транспорта, конфликт | 2–3 ч     |
| 3. Построить базовый алгоритм | Обработать заявки по входному порядку, назначить первому подходящему доступному инженеру, добавляя в конец его маршрута                        | Воспроизводимый baseline; нет нарушений ограничений                                                      | 1–2 ч     |
| 4. Реализовать оптимизатор    | Готовая библиотека или понятная эвристика; приоритет покрытия, затем число сотрудников и пробег; независимая проверка решения                  | Не менее качественный допустимый план на выбранном демосценарии; время расчёта подходит для live-демо    | 3–6 ч     |
| 5. Подключить интерфейс       | Реализовать два API-метода; заменить `src/api.ts`; передавать причины и рассчитанные времена                                                   | Путь «загрузка → план → карта → объяснение» проходит на серверном ответе                                 | 2–3 ч     |
| 6. Перепланирование           | Добавить срочную заявку, зафиксировать завершённые/начатые работы, пересчитать оставшиеся; показать diff                                       | Нет исчезнувших/дублированных заявок; прежние работы сохранены; причины отказа явные                     | 2–3 ч     |
| 7. Верификация                | Проверить ограничения, метрики, неполный план, загрузку, перепланирование и README на другом ноутбуке                                          | Контрольные сценарии проходят; результаты можно воспроизвести                                            | 1–2 ч     |
| 8. Защита                     | Подготовить историю, 6–8 слайдов, одну непрерывную демонстрацию и резервную видеозапись                                                        | Репетиция укладывается в 5–7 минут, артефакты сданы                                                      | 1–2 ч     |

## Что выяснить по исходным CSV

В папке `../Обезличивание` есть три файла «Синтетические данные» (Восток: 69 строк, Юго-восток: 86, Югоцентр: 59) и три «Контрольное распределение» (66, 83, 56 строк соответственно).

В просмотренных заголовках есть `Заявка`, типы BK/HD, `Начало`, `Окончание`, `Район`, `Адрес`, `Гигабитное подключение`; у контрольных файлов дополнительно `Статус BK` и `Бригада`. В Востоке есть дополнительное поле `Подключение`.

Следующие решения нужно согласовать с постановщиком или явно принять как допущения:

1. Означают ли `Начало`/`Окончание` окно допустимого **начала** работы или полный интервал визита? Не использовать разность автоматически как длительность.
2. Как длительность зависит от типа работы? Нужен справочник или явно обозначенные синтетические значения.
3. Как типы BK/HD соответствуют трём навыкам? Составить таблицу маппинга с обработкой неизвестных значений.
4. Откуда брать стартовые точки, смены, навыки и транспорт инженеров? Название бригады не раскрывает эти свойства.
5. Как геокодировать адреса, как проверять неоднозначные результаты и где хранить координаты? Геокодирование лучше подготовить и проверить до live-демо.
6. Есть ли достоверная связь синтетических и контрольных заявок? Нельзя предполагать совпадение по ID или позиции строки. Сначала проверить ключи и сопоставимость популяций.

Для первого полного сценария удобен **один** синтетический регион, например Юго-восток с 86 заявками. Объединение всех трёх даёт 214 строк, что превышает рекомендуемый размер кейса. Контрольные файлы не подменяют обязательный baseline: его нужно реализовать точно по заданию.

## Правила алгоритма

- Навык заявки должен быть у инженера. Если требуется транспорт, тип должен совпасть.
- Учитываются время движения, ожидание окна и длительность работы. Начало работы находится внутри окна, конец — внутри смены.
- Каждый инженер стартует из своей точки; возвращение после последней заявки не требуется.
- Каждая заявка имеет ровно один результат: назначена одному исполнителю или не назначена с объяснением.
- Сначала стремимся распределить все заявки. На сравнимых допустимых планах показываем обязательные метрики: число непустых маршрутов, пробег каждого и сумму. Веса/порядок целей команда должна объяснить, так как кейс не задаёт числовые веса.
- При неполном покрытии обязательно показываем число выполненных заявок. Сокращение пробега ценой снятых заявок нельзя выдавать за безусловное улучшение.
- Начатые работы при перепланировании фиксируются. Для инженеров в пути нужно отдельное правило; в текущем UI-демо фактическое положение не моделируется.
- Выбранный алгоритм не обязан доказывать оптимум. При ограничении времени расчёта верните лучший найденный допустимый план и честно укажите статус.

## Роли внутри команды

| Направление               | Зона ответственности                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------- |
| UX/UI и frontend          | Пользовательский путь, читаемость карты, карточки причин, diff, ошибки и загрузка, интеграция API |
| Алгоритм / backend        | Базовый расчёт, оптимизатор, ограничения, срочные события, API и объяснения                       |
| Данные / проверка         | CSV, справочники, геокодирование, синтетические дополнения, независимая проверка метрик           |
| Презентация / координация | Соответствие кейсу, README, сценарий защиты, репетиция и видеозапись                              |

При маленькой команде роли совмещаются. Выделите одного ответственного за финальную сборку и версию демоданных, чтобы UI и сервер не использовали разные наборы перед защитой.

## Сценарий защиты на 6 минут

| Время     | Что показываем                                                                  |
| --------- | ------------------------------------------------------------------------------- |
| 0:00–0:40 | Проблема диспетчера и три обязательных ограничения                              |
| 0:40–1:20 | Входной набор, инженеры, их навыки и транспорт                                  |
| 1:20–2:20 | Автопланирование, карта и расписание                                            |
| 2:20–3:10 | Одна назначенная заявка с объяснением и одна неназначенная с причиной           |
| 3:10–4:30 | Срочное событие → перерасчёт → конкретные изменения, сохранённые начатые работы |
| 4:30–5:30 | Сравнение с baseline: покрытие, персонал, пробег каждого и общий                |
| 5:30–6:00 | Допущения, инструкция запуска, следующий шаг развития                           |

## Чек-лист перед сдачей

- Исходный код в репозитории; для промежуточной сдачи уже читаются данные и работает первая версия распределения, перечислены оставшиеся задачи.
- Запуск по README воспроизведён другим участником.
- В алгоритме есть реальные проверки всех трёх групп ограничений.
- Ни одна заявка не потерялась и не продублировалась.
- Показаны причины всех отказов и объяснение выбранного назначения.
- Одно событие действительно меняет план; видно, что именно изменилось.
- Метрики пересчитаны из маршрутов, baseline соответствует постановке.
- Синтетические поля, расстояния по прямой и другие допущения обозначены явно.
- Презентация использует выданный шаблон при необходимости; есть резервное видео.
- Артефакты финальной сдачи: прототип, алгоритм, карта, объяснения, метрики, README, презентация, код.

Оценка кейса: техническая реализация 30%, подход команды 25%, соответствие задаче 20%, эффективность и удобство 15%, презентация 10%. В первую очередь доведите до конца рабочий сценарий и корректность ограничений.
